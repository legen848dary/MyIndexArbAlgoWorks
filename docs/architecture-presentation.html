01 — The Problem

Why Index Arbitrage Requires Extreme Latency

The Opportunity

Futures Drift from Fair Value

When the futures price deviates from its theoretical fair value by more than 15 BPS, a near-risk-free profit exists: buy the cheap leg, sell the expensive leg.

The arbitrage window is brief: 3–8 seconds before other participants close the gap.

+15 BPS
Minimum entry threshold
The Race

Dozens of HFT Firms Compete

Every major HFT firm — Citadel, Jump Trading, Optiver — has the same signal. The edge belongs entirely to the fastest executor.

A 2-leg basket order (1 futures + 50 constituent stocks) must be dispatched before competitors close the spread.

Orders per signal
<1ms

3–8s

The Constraint

Physics of Latency

  • Sub-µs IPC — kernel bypass via /dev/shm. Zero syscalls on hot path.
  • Zero heap allocation per tick — JVM GC pauses are milliseconds; 1000× over budget.
  • Risk checks <5µs — fat-finger, price sanity, position limit all on hot path.
  • Fixed-point arithmetic — no floating-point boxing, no BigDecimal, no rounding error.
  • Pre-interned symbols — no new String on hot path; Agrona Object2ObjectHashMap.

03 — Transport Layer

Why Aeron IPC Over Kafka or ZeroMQ?

✅ Chosen

Aeron IPC — v1.48.0

Same-host shared memory via /dev/shm

  • Sub-µs latency — kernel bypass, no syscalls on hot path
  • Lock-free SPSC ring buffer — single producer, single consumer
  • Zero-copy, zero-GC on publish and poll
  • Back-pressure via ring buffer capacity signal
  • Built-in replay via Aeron Archive API
  • PingPongTest asserts <10µs loopback over 10,000 messages
✅ Chosen: arb window is 3–8s. Every µs matters.
❌ Rejected

Apache Kafka

Distributed log — millisecond-range latency

  • 1–5ms latency (disk + network round-trip)
  • Excellent for durable, replayable event logs
  • Partitioned consumer groups, cross-host
  • Great for post-trade analytics pipeline
  • Consumer group coordination overhead
  • Wrong for <10µs hot-path signal fan-out
❌ Too slow: ~2ms vs sub-µs
❌ Rejected

TCP ZeroMQ

Socket messaging — microsecond TCP loopback

  • ~5–50µs typical (TCP loopback, OS scheduling)
  • Flexible topology — pub/sub, push/pull, dealer
  • No built-in flow control or back-pressure
  • Cross-host capable
  • Network stack jitter unpredictable under load
  • Allocation on message receive (ZMsg objects)
❌ Network stack jitter unacceptable

04 — Wire Protocol

Why SBE over Protobuf?

✅ SBE — Simple Binary Encoding
  • Flyweight pattern — decoder wraps DirectBuffer. Zero allocation on decode.
  • Field-level access — read only the fields you need; no full parse.
  • 5–10× less CPU than Protobuf for fixed-schema messages at sustained tick rate.
  • Schema versioned via templateId + schemaId; wire-compatible forward evolution.
  • LITTLE_ENDIAN native — no byte-swapping overhead on x86.
// SBE: zero-allocation decode (flyweight)
MarketDataTickDecoder tick = new MarketDataTickDecoder(); // pre-allocated
tick.wrap(buffer, offset, blockLength, version);
long price = tick.price();   // direct buffer read — zero alloc
long qty   = tick.qty();
// Total: 2 native int64 reads. No objects created.
❌ Protobuf — not for <10µs paths
  • Full deserialization — creates a complete Java object for every decode.
  • Every decode allocates — triggers GC under sustained tick rate.
  • Flexible schema evolution — excellent for cross-language REST/gRPC services.
  • Varint encoding overhead — extra CPU per variable-length field.
  • Wrong choice for hot path — right choice for cross-service APIs.
// Protobuf: allocates on every decode
MarketDataProto.Tick tick =
    MarketDataProto.Tick.parseFrom(bytes);
// ↑ new Tick object + new ByteString +
//   ArrayList for repeated fields → GC pressure
long price = tick.getPrice(); // already deserialized

⚠️ Common Pitfalls
Strata B-S Trap
BlackScholesFormulaRepository.price() boxes Double — 2 heap allocs per call. Use finmath-lib AnalyticFormulas for warm-path B-S instead.
LongAdder Trap
LongAdder has no set(value) method — it's a multi-writer counter. Use AtomicLong.setRelease() for the warm→hot bridge.
GC Validation
Each module ships a *ZeroGcTest running hot-path logic 100k times. Run with -XX:+UseEpsilonGC — JVM aborts on any allocation.
06 — Arbitrage Mechanics

Two-Leg Index Arbitrage — How It Works

1
FvEngine calculates Fair Value per tick
FV = Spot × e(r−q)T using Decimal4j long arithmetic. Dividend PV and carry cost subtracted. Result in long ×10⁴.
2
Basis = Futures Market Price − Fair Value
Published as FvUpdate [1005] with annualisedBasisBps. Positive = futures rich. Negative = futures cheap.
3
Basis > +15 BPS → Futures Rich
SELL futures (Leg 1) + BUY 50 constituent stocks (Leg 2). Convergence trade. Lock in the spread at entry.
4
Basis < −15 BPS → Futures Cheap
BUY futures (Leg 1) + SELL 50 constituent stocks (Leg 2). Reverse convergence.
5
P&L realized when basis converges to zero
Net delta = 0 (delta-1 hedge). Profit = spread captured at entry minus transaction costs. Exits within 3–8 seconds typically.

11 — Summary

5 Key Design Decisions

01

Aeron IPC over /dev/shm

Beats any network transport for co-located processes. Sub-µs latency via kernel bypass. The arb window of 3–8s demands every µs.
02

SBE Flyweights + Pre-allocated Buffers

Zero GC on the hot path. Decoder wraps DirectBuffer directly — no object creation on decode. 5–10× less CPU than Protobuf for fixed schemas.
03

Decimal4j Long Arithmetic

All prices normalized to long ×10⁴ at ingestion. No floating-point rounding error in price comparison or basis calculation. No BigDecimal allocations.
04

Three-Tier Compute Model

Hot (<10µs, zero-GC) / Warm (~30s, Strata) / Cold (batch, MC). Expensive analytics run without touching latency. AtomicLong bridge transfers results lock-free.
05

Two-Leg Delta-1 Basket Execution

Mathematically sound index arb. Net delta = 0. Profit realized on spread convergence. 51 orders per signal dispatched by BasketSlicer via RiskGateway in <1ms.
